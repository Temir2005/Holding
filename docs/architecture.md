## Структура репозитория

Корень репозитория служит корнем монорепозитория.

## Поток данных

```
Браузер ──/ru/development──▶ React Router ──▶ PageRoute
   PageRoute ──GET /api/v1/pages/development?locale=ru──▶ FastAPI
      router ─▶ PageService ─▶ ContentRepository (page + опубликованная ревизия)
                    │
                    ├─ берёт секции и SEO из снимка ревизии (черновик сайт не видит)
                    ├─ валидирует section.data по типу (discriminated union)
                    ├─ собирает все ссылки (media_id, project_ids, person_ids…)
                    ├─ грузит их пачкой (по одному запросу на тип сущности)
                    └─ разрешает LocalizedText → строка (fallback ru)
   ◀── PageRead { seo, sections: [ {type, anchor, data: развёрнутые объекты} ] }
   PageRenderer ─▶ sectionRegistry[type] ─▶ компонент секции
   SmartImage ─▶ buildImageUrl(media) ─▶ MinIO (публичный бакет)
```

Предпросмотр (`/api/v1/preview/pages/{slug}?token=`) идёт тем же путём, но снимок собирается на лету из черновика: показывает ровно то, что попадёт на сайт после публикации.

## Локали и URL

- `/` редиректит на `/ru`. Маршруты: `/:locale`, `/:locale/:slug`, `/:locale/projects/:slug`.
- Главная — страница со slug `home`.
- Неизвестная локаль ведёт на `/ru`, неизвестный slug — на 404 (тоже страница из CMS, если есть).

## Изображения

- Публичный бакет `megasmart-media` с политикой на чтение. `StorageService.public_url(key)` строит URL; в проде можно заменить на CDN или presigned без правки фронта.
- `buildImageUrl(media, { width })` на фронте сейчас возвращает `media.url`. Позже здесь подключится imgproxy.

## Локальная разработка

- Node.js и Python запускаются только в контейнерах. Код примонтирован в контейнеры, поэтому правки видны сразу.
- На macOS события файловой системы не доходят до контейнеров, поэтому Vite и uvicorn следят за файлами опросом (`VITE_USE_POLLING`, `WATCHFILES_FORCE_POLLING` в `.env`).
- `frontend/src/api/schema.d.ts` генерируется (`make gen-types`) и лежит в git, чтобы проверка типов работала без запущенного бэкенда.

## SEO и рендеринг

Сейчас SPA, мета-теги через react-helmet-async из API. Для продакшена рассмотреть пререндер (Vite SSR / vite-plugin-ssr) или переезд на Next.js: поисковики и превью в мессенджерах плохо читают SPA. Модель данных и API от этого выбора не зависят.

## Деплой (Railway)

Схема: браузер → прокси Railway → сервис `frontend` (Caddy: статика + `/api/*`) → сервис `backend` по приватной сети → Postgres и S3.

- **У бэкенда нет публичного домена.** uvicorn запущен с `--proxy-headers --forwarded-allow-ips='*'` и верит заголовкам `X-Forwarded-*` от любого источника. Если открыть бэкенд наружу, любой клиент сможет подставить себе чужой IP и обойти лимиты на вход и заявки. Бэкенд доступен только через Caddy по приватному адресу `backend.railway.internal`.
- **Один origin для браузера.** Сайт, будущая админка (`/admin`) и API открываются с домена фронтенда, Caddy проксирует `/api/*`. Поэтому refresh-cookie админки (`SameSite=Strict`, путь `/api/v1/admin/auth`) работает на `*.up.railway.app` и на собственном домене без изменений. Домены `*.up.railway.app` — публичный суффикс, cookie между двумя такими доменами не делится вообще, поэтому вариант «фронт и API на разных доменах Railway» не работает.
- **IP клиента.** Прокси Railway передаёт адрес клиента в `X-Forwarded-For`. Caddy доверяет только прокси Railway (`trusted_proxies`: частные адреса и `100.64.0.0/10`), берёт клиента справа в цепочке и отдаёт бэкенду один адрес (`X-Forwarded-For: {client_ip}`). Без этого бэкенд видел бы адрес прокси и считал всех посетителей одним клиентом. Если в логе окажутся адреса прокси, их диапазон нужно добавить в `trusted_proxies`. После деплоя проверить: в логе бэкенда в строках запросов должен быть реальный IP, а не адрес из приватной сети.
- **Адрес, который слушает бэкенд (открытый вопрос).** В `backend/Dockerfile` стоит `--host ::`. asyncio для `::` включает режим «только IPv6», и по IPv4 бэкенд недоступен: локально Caddy получает отказ в соединении. Приватная сеть Railway раньше была только IPv6, поэтому на Railway это может работать, но проверка здоровья и IPv4-соединения не пройдут. Правка Dockerfile ждёт согласования.
- **Переменные окружения бэкенда:** `APP_ENV=production`, `JWT_SECRET` и `LEAD_IP_SALT` длиной от 32 символов. Вне `dev` приложение со слабыми значениями не стартует.
- **Хранилище:** `S3_ENDPOINT_URL` — адрес для бэкенда (внутренний), `S3_PUBLIC_URL` — для картинок в браузере, `S3_PRESIGN_ENDPOINT_URL` — хост в ссылках загрузки (по умолчанию `S3_PUBLIC_URL`). Ссылки подписываются SigV4, хост входит в подпись, поэтому он должен быть доступен браузеру. Бакету нужно правило CORS на `PUT` с домена сайта (`docs/admin-api.md`, «Медиатека»).
- **Pre-deploy:** `alembic upgrade head`, затем сиды, если `SEED_ON_DEPLOY=true`. Сиды наполняют только пустую базу (нет `site_settings`), на рабочей ничего не меняют, поэтому флаг можно не выключать. `python -m app.cli cleanup` чистит незавершённые загрузки и старые refresh-токены — его стоит добавить в pre-deploy или в расписание.
- **Первый администратор:** `python -m app.cli create-admin --email … --name …` в консоли сервиса бэкенда.
- **Если API когда-нибудь понадобится на отдельном поддомене** (`api.megasmart.kz` + `admin.megasmart.kz`): общий родительский домен, cookie с `Domain=megasmart.kz` и `SameSite=Lax`, CORS с `credentials`, проверка заголовка `Origin` на `/auth/refresh`, и обязательно сузить `--forwarded-allow-ips` до адресов прокси.

## Админка (CMS)

Админское API `/api/v1/admin/*` — описание для интерфейса в `docs/admin-api.md`, модель данных в `docs/content-model.md`. Интерфейс админки — следующий этап; API описывает себя само (`GET /admin/meta`, `GET /admin/section-types` с подсказками для форм), поэтому формы строятся без дублирования схем во фронте.

Устройство:

- **Слои те же:** роутеры (без логики) → сервисы → репозитории → модели. Сервисы бросают доменные ошибки (`app/core/errors.py`), один обработчик переводит их в `{error: {code, message, details}}` — только для `/admin` и `/preview`; публичное API отвечает как раньше.
- **Базовый CRUD** (`app/services/admin/base.py`): проверка `version` под блокировкой строки (`SELECT … FOR UPDATE`), транзакция с откатом при ошибке, запись в журнал в той же транзакции, новые записи в конец списка. Сервис сущности описывает только своё: как собрать строку (`build`), как отдать (`present_many`, связанные карточки грузятся пачкой и передаются явно), что проверить (`validate(obj, before)`). Состояния между вызовами в сервисах нет.
- **Документы в JSONB** (данные секций, настройки) проверяются теми же Pydantic-моделями, что читают их для сайта. Проверки, которые нужны только при записи (ссылки существуют, обязательные тексты, правила между полями), — в сервисах: иначе одна старая запись могла бы уронить публичную страницу.
- **Ссылки:** `Ref` (по id) и `KeyOf` (по ключу: slug направления, набор цифр) помечают поля в схемах. По этим пометкам работают проверка при сохранении, подсказки для форм, разворачивание в ответе и поиск использования (`UsageFinder`): удалить или переименовать то, на что ссылаются черновики, опубликованные версии, меню или коллекции, нельзя.
- **Публикация:** снимок страницы в `page_revision`, сайт читает только его. Черновик сравнивается со снимком (`has_unpublished_changes`), публикация защищена хешем черновика от чужих непросмотренных правок.
- **Вход:** пароли argon2, access-токен JWT на 15 минут, refresh-токен — httpOnly cookie с ротацией и отзывом всей сессии при повторном использовании. Подробно — `docs/admin-api.md`, «Вход».
- **Медиа:** браузер грузит файл прямо в S3 по presigned PUT; на `complete` сервер проверяет тип по содержимому, вырезает метаданные, очищает SVG и делает WebP-копии. Тяжёлая обработка идёт в отдельном потоке и без блокировки строки.
- **Кэш:** публичные `GET` — `ETag` + `max-age=0, must-revalidate` (`app/api/cache.py`): изменение видно сразу после публикации, неизменная страница стоит 304 без тела. Админка и предпросмотр — `no-store`.
- **Сиды** (`seed/run.py`) — только начальное наполнение пустой базы, в одной транзакции под advisory-блокировкой; `make seed-force` перезаписывает стартовый контент и работает только при `APP_ENV=dev`.
- **Тесты** строят схему миграциями, а не `create_all`; `alembic check` следит, чтобы модели и миграции не расходились. Хранилище в тестах — `InMemoryStorage`.

## Сознательно отложено

Решения, принятые осознанно. Здесь — почему и что делать, когда понадобится.

- **UI-строки во фронтенде, а не в CMS.** Подписи кнопок, полей формы, статусов и страницы 404 лежат в `frontend/src/i18n/*.json`. Это интерфейс, а не контент: меняются вместе с кодом и проверяются типами. Всё, что редактор должен менять (тексты формы заявки, согласие, сообщение об успехе), — в блоке `contact_form`. Если понадобится править UI-строки без деплоя — отдельная таблица переводов с отдачей через API и загрузкой в react-i18next.
- **Конструктор форм.** Форма одна, поля фиксированы моделью `lead`. Произвольные формы — это три таблицы (форма, поле, ответ), проверка по описанию, выгрузка по каждой форме и динамический рендер на фронте: 2–3 этапа. Темы обращения и тексты формы уже редактируются.
- **Корзина.** Удаление окончательное. Защищает: запрет удалять используемое (`409 IN_USE`), полный снимок удалённой записи в журнале, история версий страниц. При удалении страницы её версии удаляются вместе с ней — последнее состояние остаётся только в журнале. Если понадобится: колонка `deleted_at` и фильтр в репозиториях.
- **Предпросмотр во фронтенде.** API готово (`preview-token`, `GET /api/v1/preview/pages/{slug}`), но маршрута сайта `/preview/:slug?token=…` пока нет. Сделать вместе с интерфейсом админки, после `make gen-types`.
- **Заголовки в ответе 304.** Ответ 304 сейчас несёт только `ETag` и `Cache-Control`. Остальные заголовки ответа 200 он теряет, в том числе `Vary: Origin` и CORS-заголовки, которые добавляет `CORSMiddleware` при запросе с другого origin. По RFC 9110 в 304 нужно повторять `Vary` (и `Date`, `Expires`, `Content-Location`). Сейчас это не мешает: сайт и API открываются с одного origin, CORS не участвует. Если появятся общий кэш (CDN) или кросс-доменные запросы — копировать эти заголовки из исходного ответа в 304 в `app/api/cache.py`.
- **Ссылка на загрузку действует до истечения срока.** Presigned PUT живёт 15 минут, и `complete` её не отзывает: S3 не умеет отменять подписанные ссылки, поэтому по ней можно перезаписать уже проверенный файл. Риск ограничен (ссылку получает только вошедший редактор, ключ случайный, срок короткий). Закрыть полностью: грузить во временный ключ `uploads/<uuid>`, а на `complete` копировать проверенный файл в постоянный и удалять временный.
