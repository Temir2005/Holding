# Интерфейс админки

Админка живёт во фронтенде по адресу `/admin` и работает с админским API (`docs/admin-api.md`). Формы она не описывает сама: блоки, коллекции, страницы, медиа и настройки строятся по JSON Schema, которую отдаёт бэкенд. Поэтому новый тип блока или новое поле появляются в админке без правки её кода.

## Где живёт и как отделена от сайта

- **Вход** — `frontend/src/admin/route.tsx`. Роутер сайта загружает его лениво (`{ path: '/admin/*', lazy: … }` в `src/app/router.tsx`), поэтому в бандл сайта не попадают ни код, ни стили, ни строки админки. Это видно по сборке: размер JS сайта не меняется от правок админки.
- **Разделы — отдельные чанки.** Каждый раздел грузится, когда его открывают (`sectionLoaders.ts`, `sections.tsx`). Стартовый чанк (вход, каркас, сессия) весит около 65 КБ gzip. После входа остальные разделы догружаются в простое браузера, поэтому переходы мгновенные. В dev-сервере зависимости разделов собираются заранее (`optimizeDeps.entries` в `vite.config.ts` обходит `src/admin`): иначе Vite находил бы их только при первом открытии раздела и перезагружал все вкладки.
- **Стили.** Корень админки — элемент с классом `.admin`. У админки свой конфиг Tailwind (`tailwind.admin.config.ts`, `important: '.admin'`) и свои токены `--a-*` (`styles/admin.css`). Светлая и тёмная темы задаются атрибутом `data-theme`, по умолчанию тема следует системной. При входе в админку класс `<body>` сайта подменяется, а при выходе восстанавливается (`layout/theme.ts`).
- **Строки интерфейса** лежат в отдельном пространстве i18n `admin` (`i18n/ru.json`), только на русском. Язык фиксирован (`useT`, `tAdmin`), язык сайта на админку не влияет.
- **Индексация.** У админки всегда стоит `<meta name="robots" content="noindex, nofollow">`, независимо от прокси.

## Структура папок

```
frontend/src/admin/
  route.tsx           # провайдеры, маршруты, роли
  sectionLoaders.ts   # import() каждого раздела и фоновая догрузка
  sections.tsx        # React.lazy по разделам
  api/                # client.ts (типизированный клиент), tokens.ts (обновление токена),
                      # errors.ts, queries.ts (ключи и общие запросы), refCards.ts,
                      # по модулю на раздел: pages, media, collections, leads, users, audit, settings
  session/            # вход, восстановление сессии, RequireAuth / RequireRole, смена пароля
  layout/             # каркас: меню (nav.ts), шапка, нижняя панель телефона, тема
  ui/                 # Button, Dialog/Sheet, Menu, Field, Input, Switch, Toast, Confirm,
                      # feedback (Badge, Alert, Skeleton, EmptyState, ErrorState)
  forms/              # конфликты версий и IN_USE, guards (несохранённое, Cmd+S),
                      # EntityPicker, ссылки на места использования (usage.ts)
  forms/schema/       # SchemaForm: resolve.ts, validate.ts, values.ts, errors.ts,
                      # registry.ts, widgets/*
  features/           # dashboard, pages, media, collections, leads, settings, users, audit
  i18n/ru.json
  styles/admin.css
  test/               # fakeApi (fetch по маршрутам), renderForm/withProviders
frontend/e2e/         # Playwright: сценарии по разделам, sweep.spec.ts (вёрстка, axe)
```

## Данные и запросы

- **Клиент** (`api/client.ts`). Пути, параметры и ответы берутся из сгенерированного `src/api/schema.d.ts` (`make gen-types`), руками ничего не повторяется: `api.get('/api/v1/admin/pages/{page_id}', { path: { page_id } })`. Общий список коллекций работает через нетипизированный `request`, а тип записи задаёт объявление коллекции (см. ниже).
- **Токен.** Access-токен хранится только в памяти, refresh-токен — в httpOnly-cookie. Обновлением занимается одно место, `TokenManager` (`api/tokens.ts`): все параллельные запросы вкладки ждут одно обновление, а вкладки договариваются через `navigator.locks`. Без них используется `BroadcastChannel`, а при его отсутствии обновление идёт только внутри вкладки. На 401 токен обновляется один раз и запрос повторяется, иначе пользователь попадает на вход с возвратом на ту же страницу.
- **Ошибки.** Любой ответ с ошибкой превращается в `AdminApiError {status, code, message, details}`. Интерфейс реагирует на `code` (`ErrorCode` в `api/errors.ts`), а `message` от сервера уже написан для людей и показывается как есть.
- **TanStack Query.** Все ключи начинаются с `['admin', …]` (`adminKey`), при выходе кэш админки очищается. Справочники (`meta`, `section-types`, `entity-types`) кэшируются надолго.
- **Карточки ссылок** (`api/refCards.ts`). Карточки объектов, на которые ссылаются поля (файл, проект, человек), кэшируются поштучно. Страница и запись коллекции приносят их сразу, выбор в окне добавляет новые, а недостающие догружаются одним `lookup?ids=`.

## Формы по схеме

`SchemaForm` (`forms/schema/SchemaForm.tsx`) получает JSON Schema и строит форму на react-hook-form. Результат отдаётся в хранимом виде: пустые языки отбрасываются, необязательный текст без языков становится `null`.

Откуда берутся схемы:

| Что редактируется | Схема |
|---|---|
| Данные блока | `GET /admin/section-types`, тип блока |
| Настройки блока (якорь, фон, видимость) | `GET /admin/entity-types`, `section` |
| Страница (адрес, название, SEO) | `entity-types`, `page` |
| Файл медиатеки | `entity-types`, `media` |
| Записи коллекций | `entity-types`, `division`, `project`, `person`, `client`, `timeline_event`, `stat`, `vacancy` |
| Настройки сайта | `entity-types`, `site_settings` |

Как работает форма:

- **Выбор редактора.** `resolve.ts` раскрывает `$ref` и `anyOf [X, null]`, затем `fieldKind` выбирает вид поля по подсказкам: `x-widget`, `x-ref`, `x-options`, `x-enum-labels`, а без подсказок — по типу. Компонент для каждого вида берётся из реестра (`registry.ts`, `widgets/index.ts`). Неизвестный виджет становится полем JSON с предупреждением в консоли, данные при этом не теряются.
- **Проверка на клиенте** (`validate.ts`) повторяет правила схемы: `required`, длины, `pattern`, границы чисел, `enum`. Для русского текста обязательна только версия на русском. Сервер всё равно проверяет всё ещё раз.
- **Ошибки сервера.** `applyServerErrors` переводит `loc` из 422 в путь поля (`body.data.steps.0.title.ru` → `data.steps.0.title.ru`). Если такого поля нет, ошибка показывается над формой.
- **Версии.** Каждое сохранение отправляет `version`. На `409 VERSION_CONFLICT` появляется диалог «Загрузить свежую версию» / «Остаться и скопировать свои правки», чужие правки молча не затираются. Если новая версия пришла фоном и правок нет, она показывается сразу. Если правки есть, они остаются в форме, а сохранение откроет диалог.
- **Несохранённые правки.** При уходе со страницы и закрытии вкладки появляется предупреждение (`useUnsavedGuard`), Cmd/Ctrl+S сохраняет форму (`useSaveShortcut`).
- **Языки.** Над формой один переключатель RU/KZ/EN с отметками, какие языки заполнены. Пустой KZ/EN показывает русский текст как подсказку.

## Разделы

| Раздел | Код | Что важно |
|---|---|---|
| Главная | `features/dashboard` | новые заявки, неопубликованные изменения, журнал (admin), быстрые действия с загрузкой файлов |
| Страницы | `features/pages` | список с порядком; редактор: блоки, настройки и SEO, предпросмотр (iframe `/:locale/preview/:slug`), публикация с `draft_hash`, история, удаление; `?block=<id>` открывает блок |
| Медиатека | `features/media` | сетка и список, загрузка в три шага, карточка файла (`?file=<id>`), тот же браузер в окне выбора |
| Коллекции | `features/collections` | один список и один редактор на все семь коллекций, отличия — в `config.tsx` |
| Заявки | `features/leads` | фильтры в адресе, статус в один клик, заметка, CSV; `?lead=<id>` открывает заявку |
| Настройки сайта | `features/settings` | только admin, сохраняются целиком |
| Пользователи | `features/users` | только admin; себя нельзя отключить или лишить роли admin, интерфейс объясняет это заранее |
| Журнал | `features/audit` | только admin; «было → стало», названия полей из форм |

Общие правила для экрана:

- заголовок задаёт `PageTitle`: он ставит `<h1>` и название вкладки браузера;
- пока данные грузятся, виден `Skeleton`;
- если данных нет, показывается `EmptyState` с действием;
- при ошибке загрузки — `ErrorState` с кнопкой «Повторить»;
- фильтры и открытая запись живут в адресе, чтобы ссылку можно было отправить и вернуться назад.

## Как добавить виджет

Пример — поле телефона с маской, `x-widget: phone`.

1. **Бэкенд.** Пометить поле схемы: `phone: str | None = field("Телефон", widget="phone", default=None)`. Хелпер `field` (`backend/app/schemas/fields.py`) кладёт подсказку в JSON Schema. Список подсказок описан в docstring этого файла.
2. **Вид поля.** Добавить `'phone'` в `FieldKind` (`forms/schema/types.ts`) и в `WIDGET_KINDS` (`forms/schema/resolve.ts`).
3. **Компонент** — `forms/schema/widgets/PhoneField.tsx`, принимает `WidgetProps` (`name`, `node`, `required`, `label`, `description`). Значение берётся через `useController({ name })`, ошибка — через `useFieldError(name)`. Обёртка `Field` из `ui/Field.tsx` связывает подпись, подсказку и ошибку с элементом управления. Цели нажатия на телефоне должны быть не меньше 44 px (`min-h-touch`).
4. **Регистрация** — `registerWidget('phone', PhoneField)` в `widgets/index.ts`.
5. **Проверка на клиенте.** Если значение — строка, добавить `case 'phone'` к строковым видам в `validate.ts`. Если у виджета свой пустой вид значения, поправить `emptyValue` в `values.ts`.
6. **Тесты.** Тест виджета в `SchemaForm.test.tsx`. Затем `make gen-types` и пересборка фикстур схем (`forms/schema/__fixtures__`). Тесты «все типы блоков без JSON-полей» (`pages.test.ts`, `collections.test.ts`, `settings.test.tsx`) упадут, если подсказка осталась без редактора.

## Как добавить раздел

Пример — «Отзывы» по адресу `/admin/reviews`.

1. **Страница** — `features/reviews/ReviewsPage.tsx`. Внутри: `PageTitle`, состояния загрузки, пустоты и ошибки, на телефоне карточки вместо таблицы. Запросы — в `api/reviews.ts` через `queryOptions` и ключи от `adminKey`.
2. **Чанк.** Загрузчик в `sectionLoaders.ts` (`reviews: () => import('./features/reviews/ReviewsPage')`), ленивый компонент в `sections.tsx`.
3. **Маршрут** — в `route.tsx`. Раздел только для admin оборачивается в `<RequireRole role="admin">`.
4. **Меню** — пункт в `NAV` (`layout/nav.ts`) с иконкой lucide и ролью. Боковое меню, колонка иконок на планшете и «Ещё» на телефоне строятся из этого списка. Если раздел нужен в нижней панели телефона, добавить его в `BOTTOM_BAR`.
5. **Строки** — `i18n/ru.json`: `nav.reviews` и строки раздела.
6. **Тесты.** Компонентные тесты рядом с кодом через `withProviders` и `fakeFetch` (`test/`). В `e2e/sweep.spec.ts` добавить раздел в `SECTIONS`: тогда он проверяется на 375/768/1280/1920 px (нет горизонтальной прокрутки, у всех элементов управления есть имя) и axe-ом в светлой и тёмной теме.

## Как добавить коллекцию

Бэкенд описан в `docs/content-model.md` («Как добавить коллекцию»): модель, миграция, схемы, репозиторий, сервис, роутер. Для админки к этому добавляется следующее.

**Бэкенд, форма.**
1. Класс `AwardForm` в `backend/app/schemas/admin/collection_forms.py`:
   - те же поля, что в `AwardUpdate`, с русскими названиями;
   - подсказки: `widget`, `Ref(...)` с `accept` для файлов, `labels` для вариантов, `options` для подсказок из `meta`.
2. Строка в `COLLECTION_FORMS`.
3. Связь со службой: `form = AwardForm` в `AwardService`, тогда при сохранении проверяется и вид файлов.
4. Тест `test_collection_forms.py` (словарь `UPDATES`) следит, чтобы поля формы совпадали с `PATCH`.

**Фронтенд.**
1. `make gen-types`, затем пересборка фикстуры `entity-types.json`.
2. `{ slug: 'awards', icon: Award }` в `COLLECTIONS` (`layout/nav.ts`). Slug — это и путь API, и адрес в админке.
3. Объявление в `COLLECTION_CONFIGS` (`features/collections/config.tsx`). Тип записи — `components['schemas']['AwardAdminRead']`. В объявлении задаются:
   - как называется запись (`title`, `subtitle`, `thumb`);
   - колонки;
   - фильтры: по `meta`, по `lookup` или да/нет;
   - сортировки (только те, что разрешает репозиторий);
   - можно ли перетаскивать и в каких группах;
   - ссылка на сайт;
   - поле с отдельным сохранением, как галерея проекта;
   - подстановка из подсказок (`prefill`), как отрасль клиента.
4. `award: 'awards'` в `COLLECTION_OF` (`forms/usage.ts`), чтобы места использования открывались ссылкой.
5. Строки: `collections.awards` (меню) и `collection.new.awards` («Новая награда»).
6. Тесты:
   - `collections.test.ts` проверяет, что у каждой коллекции меню есть объявление и форма без JSON-полей;
   - сценарий раздела в e2e — по образцу `collections.spec.ts`.

Список, поиск, фильтры, переключатель «На сайте», перетаскивание, удаление с местами использования, конфликты версий и форма появятся сами.

## Новый тип блока

Админке ничего не нужно. Тип описывается на бэкенде (`docs/content-model.md`, «Как добавить тип секции»), и после этого:
- он появляется в окне «Какой блок добавить?»;
- форма строится по его схеме;
- выбор сущностей и файлов работает по `x-ref`.

На сайте нужен только компонент секции в `sectionRegistry`. Если админка старше бэкенда и тип ей неизвестен, блок всё равно открывается: его данные можно править как JSON.

## Проверки

- **`make lint`** — eslint и `tsc` для фронта (вместе с ruff и mypy).
- **`make test`** — vitest для фронта (вместе с pytest): SchemaForm и виджеты, разбор ошибок и `loc`, обновление токена, компонентные сценарии разделов.
- **`make e2e`** — Playwright в отдельном compose-проекте `megasmart-e2e`: своя база и бакет, наполнение сидами с нуля, после прогона всё удаляется. Dev-база не затрагивается. Отдельные тесты: `make e2e ARGS="e2e/sweep.spec.ts"`.
  - **Обход** (`sweep.spec.ts`): все разделы на 375/768/1280/1920 px — нет горизонтальной прокрутки, у кнопок, ссылок и полей есть доступное имя. Плюс axe (`@axe-core/playwright`, WCAG 2.1 A/AA, контраст и ARIA) на всех разделах и в открытых панелях, в светлой и тёмной теме.
  - **Скриншоты** складываются в `frontend/e2e/screenshots/`, в git они не попадают.
- **Бандл.** После правок полезно собрать проект (`docker compose … exec frontend npx vite build`) и убедиться, что JS сайта (`index-*.js`) не вырос: код админки туда попадать не должен.
