## Задача

В проекте уже есть рабочий прототип: публичное API на FastAPI, которое только читает, и фронтенд на React, который рисует страницы из секций. Контент попадает в базу только через `make seed`.

Нужно достроить бэкенд до **полноценной CMS**: весь текст, все изображения и все интерактивные элементы сайта должны создаваться, меняться и удаляться через админское API — без правки кода, без сидов и без деплоя. Если что-то на сайте нельзя изменить через API — задача не выполнена.

В этой задаче — только бэкенд и админское API (`/api/v1/admin/*`). Интерфейс админки будет отдельным этапом, но API проектируй так, чтобы интерфейс строился поверх него почти автоматически.

Код должен остаться таким же чётким и читаемым, как сейчас: **продолжай существующую архитектуру, а не строй новую рядом**.

## Что уже есть — на это опирайся

Сначала прочитай `CLAUDE.md`, `docs/architecture.md`, `docs/content-model.md`, затем код в `backend/app`.

- **Слои**: `api/routers/{public,admin}` → `services` → `repositories` → `models`, схемы в `schemas/`. Папка `api/routers/admin/` пока пустая — она ждёт эту задачу.
- **Модели** (`models/`): `Page`, `Section`, `SiteSettings` (одна строка; навигация, контакты, соцсети, подвал и SEO лежат в JSONB), `Media`, `Division`, `Project` + `ProjectMedia`, `Person`, `Client`, `TimelineEvent`, `Stat`, `Vacancy`, `Lead`. Примеси `IdMixin`, `TimestampMixin`, `PublishableMixin` (`is_published`, `sort_order`).
- **Секции** (`schemas/sections.py`): 22 типа. У каждого пара моделей — хранимая (`*Data`, наследник `Stored`, `extra="forbid"`) и для чтения (`*DataRead`) — и запись в реестре `SECTION_SCHEMAS`. `Section.type` — строка, а не enum в Postgres, чтобы новый тип не требовал миграции.
- **Ссылки** (`schemas/refs.py`): поле с аннотацией `Ref(RefKind.media, "background")` хранит id, а `collect_refs` и `expand` при отдаче подставляют полные объекты пачкой. Ссылки на удалённые сущности молча пропускаются.
- **Переводы** (`core/i18n.py`): `LocalizedText`, в базе — JSONB `{"ru", "kk", "en"}`, запасной язык `ru`.
- **Хранилище** (`storage/service.py`): `StorageService` c `upload`, `public_url`, `presigned_put_url`. Публичный бакет на чтение. Нет удаления, проверки существования и чтения объекта.
- **Форматированный текст** — Markdown (`Project.body`, секция `about_text`), фронт рисует его компонентом `Markdown`.
- **Заявки**: `POST /leads`, ограничитель частоты в памяти процесса, хеш IP.
- **Тесты**: отдельная база Postgres, таблицы создаются через `Base.metadata.create_all`.
- **Деплой**: Railway, перед выкладкой запускается `alembic upgrade head` и, если `SEED_ON_DEPLOY=true`, сиды.

### Проблемы, которые нужно учесть
1. **Сиды затирают контент.** `Seeder.upsert` делает `merge` по детерминированным id, а `Seeder.page` удаляет секции, которых нет в сидах. После появления админки запуск `make seed` (в том числе на деплое) уничтожит правки редакторов. Сиды должны стать начальным наполнением: по умолчанию не трогать существующие строки, перезапись — только с явным флагом. Предложи решение на этапе 0.
2. **Тесты не проверяют миграции**: схема создаётся из моделей. Добавь проверку, что миграции и модели не расходятся (`alembic check` или тест с `upgrade head`).
3. **`jwt_secret` и `lead_ip_salt` по умолчанию `change-me`**: вне dev-режима приложение должно отказываться стартовать с такими значениями.
4. **Мусор в репозитории** (`frontend/.vite/deps/` в git, `requirements.txt` в корне рядом с `uv`) — ничего не трогай, просто упомяни в отчёте этапа 0.

## Что должна уметь CMS

### 1. Вход и права
- Таблица пользователей админки, роли `admin` (всё, включая пользователей и настройки сайта) и `editor` (контент и медиа).
- Пароли — argon2. Короткий access-токен (JWT) + refresh-токен в httpOnly cookie с ротацией и отзывом; выход, смена пароля.
- Ограничение частоты попыток входа (переиспользуй `RateLimiter`, вынеси его из `services/leads.py` в `core/`).
- Первый администратор создаётся командой CLI (`python -m app.cli create-admin`), открытой регистрации нет.
- Зависимости `require_editor` / `require_admin` в `api/deps.py`. Все админские роутеры закрыты ими на уровне роутера, а не каждого эндпоинта.
- **Журнал действий**: кто, когда, какую сущность и как изменил (с разницей до/после). Запись — в сервисном слое, в той же транзакции.

### 2. Страницы и секции
- CRUD страниц (slug, название, SEO, og-картинка, публикация, порядок).
- CRUD секций: создать, изменить, удалить, **скопировать**, скрыть/показать, **изменить порядок одним запросом** (`PUT /admin/pages/{id}/sections/order` со списком id).
- `data` проверяется хранимой моделью из `SECTION_SCHEMAS`; ошибка возвращается с путём до поля.
- При сохранении проверяй, что все id в полях `Ref` существуют (публичное API пропускает битые ссылки молча, а админка должна сообщать об ошибке).
- Админское чтение отдаёт данные **в хранимом виде**: все языки и id ссылок, плюс рядом — краткие карточки объектов, на которые ссылается секция (название и превью), чтобы интерфейс мог их показать.
- **`GET /admin/section-types`** — главный механизм для будущей админки. Для каждого типа: название, описание и JSON Schema хранимой модели с подсказками для интерфейса:
  - `LocalizedText` → виджет многоязычного текста (однострочный или многострочный);
  - Markdown-поля → виджет редактора Markdown;
  - поля `Ref` → выбор сущности с указанием `RefKind` и признаком «один / список»;
  - `Literal` → выпадающий список с подписями;
  - иконки → выбор из списка допустимых (сверь с `frontend/src/components/ui/Icon.tsx`; список допустимых имён должен проверяться на бэкенде).

  Подсказки задавай декларативно рядом с полем (через `Field(json_schema_extra=...)` или аннотации, как `Ref`), а не отдельной таблицей соответствий. Подписи полей и типов секций — на русском.
- Добавление нового типа секции должно остаться таким же простым: две модели + строка в реестре.

### 3. Коллекции
Полный CRUD для `Division`, `Project` (включая упорядоченную галерею), `Person`, `Client`, `TimelineEvent`, `Stat`, `Vacancy`:
- списки с постраничной выдачей, поиском, фильтрами и сортировкой;
- изменение порядка одним запросом;
- публикация и снятие с публикации;
- проверка уникальности slug с понятной ошибкой.

Повторяющийся CRUD вынеси в общие базовые классы репозитория и сервиса, но без «магии»: код конкретной сущности должен читаться сам по себе. `ContentRepository` сейчас обслуживает публичное чтение — не раздувай его, админские репозитории делай отдельно.

### 4. Настройки сайта и навигация
- `GET/PUT /admin/settings`: название, логотип, навигация, контакты, соцсети, подвал, SEO по умолчанию — с проверкой схемами из `schemas/site.py`.
- При сохранении проверяй, что `page_slug` в пунктах меню и в кнопках (`Cta`) указывает на существующую страницу.
- Список языков сайта и язык по умолчанию сейчас зашиты в `core/i18n.py` — оставь так, но отдавай их в `GET /admin/meta` вместе с перечислениями (`ProjectStatus`, `EmploymentType`, `LeadType`, `Tone`, типы соцсетей, иконки), чтобы интерфейс ничего не дублировал.

### 5. Медиатека (S3)
- Загрузка в три шага: `POST /admin/media/upload-url` (проверка типа и размера, выдача presigned URL и ключа) → браузер грузит файл прямо в S3 → `POST /admin/media/{id}/complete` (сервер проверяет, что объект есть, читает **реальные** тип и размеры через Pillow, считает `dominant_color`). Незавершённые загрузки не видны в медиатеке и чистятся.
- Белый список типов: jpeg, png, webp, avif, svg, mp4, pdf. Лимит размера — из настроек. SVG очищается от скриптов.
- Ключи в S3 — случайные (`media/{yyyy}/{mm}/{uuid}.{ext}`), исходное имя файла хранится в записи.
- Дополни `StorageService` методами удаления, проверки и чтения объекта. В тестах хранилище подменяется реализацией в памяти.
- Запись `media`: добавь исходное имя файла, папку или теги, статус загрузки. Редактирование `alt` на всех языках.
- **Запрет удаления используемых файлов**: перед удалением ищи файл во внешних ключах и в JSONB секций и настроек (через тот же `collect_refs`). Если используется — 409 со списком мест. Удаление записи удаляет и объект в S3.
- Список с поиском, фильтром по типу и папке, постраничной выдачей.
- Уменьшенные версии картинок — см. «Решения на согласование».

### 6. Заявки
- Список с фильтрами (тип, дата, статус), просмотр, смена статуса (`new` / `in_progress` / `done` / `spam`), заметка менеджера, выгрузка CSV.
- Тексты формы, кнопки и сообщения об успехе уже лежат в секции `contact_form` — убедись, что всё редактируется.

### 7. Публикация, история, предпросмотр
- Правка опубликованной страницы не должна сразу попадать на сайт: редактор сохраняет черновик и публикует отдельным действием.
- История версий страницы с откатом.
- Предпросмотр черновика по короткоживущему токену: `GET /api/v1/preview/pages/{slug}?token=...` — в том же формате, что и публичная страница.
- Защита от затирания чужих правок: поле `version` у редактируемых сущностей, устаревшая версия → 409.

Конкретную схему согласуй на этапе 0 (см. ниже).

### 8. Качество API
- Единый формат ошибок `{ "error": { "code", "message", "details" } }` для админского API; ошибки проверки — со списком полей. Доменные исключения в `core/errors.py`, перевод в HTTP — в одном обработчике, а не `HTTPException` в сервисах.
- Единый формат списков: `items`, `total`, `page`, `page_size`.
- У каждого эндпоинта — тег, краткое описание, модели ответа и ошибок. Админские эндпоинты в OpenAPI отделены тегами от публичных.
- Для каждой сущности отдельные схемы `Create`, `Update`, `AdminRead`. Существующие `*Read` для публичного API не меняй.
- Кэш публичного API: заголовки `Cache-Control` и `ETag`; после публикации данные обновляются сразу.

## Тесты и проверки

- Вход, роли, отказ без токена и с чужой ролью.
- Секции: верные и неверные данные по нескольким типам, битая ссылка, порядок, копирование.
- `section-types`: схема каждого типа из реестра строится и содержит подсказки для `LocalizedText` и `Ref`.
- CRUD коллекций на одной-двух сущностях + общий параметризованный тест на остальные.
- Медиа: загрузка с хранилищем в памяти, подмена типа файла, запрет удаления используемого файла.
- Публикация: черновик не виден публично, публикация, откат, предпросмотр, конфликт версий.
- Сиды не затирают изменённый контент.
- **Существующие тесты публичного API проходят без изменений** — это проверка, что фронт не сломан.

После каждого этапа запускай `make lint` и `make test` и показывай результат. Не ослабляй настройки `ruff` и `mypy`, не ставь `# type: ignore` без объяснения.
